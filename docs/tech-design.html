AI + Web 赛道 / AI 与健康 版本：1.0　最后更新：2026-11-04

一、项目概述

1.1 一句话

把家族口述的病史整理成一张家系图，算出你的风险里有多少是「能拿回来的」，并给出这周就能做的一步。

1.2 要解决的问题

一个人去做体检，报告写着「未见异常」。但他心里清楚：父亲 52 岁放了心脏支架，爷爷有糖尿病，外婆是脑溢血走的。

这些信息存在，却没有去处：

  • 体检报告只解读当次指标，不看家族；
  • 医院问卷问「家族史：有 / 无」，把最重要的三个维度（谁、几岁发病、几个亲属）全部丢掉；
  • 健康 App 给建议，但从不说「我这么改到底图什么」，也从不复算；
  • 家系图这个工具在临床用了六十年，医生画在病历本上，患者一辈子见不到第二次。

结果是：信息在，判断不在，行动更不在。

1.3 目标用户

30–45 岁、家里有慢病或肿瘤患者、会用网页但看不懂体检报告的成年子女。

这个人群有一个特殊结构：使用者与受益者不是同一个人。用户在为父母负责，而父母往往不配合。所以产品必须做到：能替他梳理、能给他能转发的东西、能告诉他「先说服谁去查什么」。

二、需求分析

2.1 真实场景

时刻 用户在想什么 产品要给出什么
父亲刚放完支架 「我会不会也一样」 我的风险是多少，其中多少改不了
拿到体检报告 「未见异常，但我总觉得不对」 标准体检漏了什么
想改变生活习惯 「知道该动，但不知道从哪开始」 这周具体做哪一件
三个月后 「我这么折腾有用吗」 重新算一遍，数字动了没有

2.2 现有方案的不足

方案 缺什么
家族史问卷 三个维度全丢，答完给一个说不出依据的分数
遗传咨询门诊 专业，但只有大三甲有，排不上，且多数人不需要遗传咨询，需要的是一次正确的筛查
体检报告解读 只解读已有指标，不看家族
健康管理 App 只给建议，不给可验证的目标，也不复算，第三周就被卸载

空白：家系图存在六十年、方法成熟，却从未有一个面向家庭的数字化版本；而现有健康产品又只给建议、不给可验证的目标。

2.3 功能需求

  1. 口语输入 → 结构化家系节点（支持模糊、省略、改口、否定）
  2. 家系图实时可视化，节点可点、依据可查、可删除
  3. 从家系中读出家族史等级，接入风险量化
  4. 风险拆解为「改不了的」与「可回收的」
  5. 生成可执行的行动方案（最小动作，非方向）
  6. 每个数字可追溯出处

2.4 非功能需求

需求 约束 实现方式
隐私 家族病史属敏感信息 全链路本地推理，数据不出本机
安全 不得给出诊断或绝对概率 只输出相对分层，不输出个人化概率
可信 每个数字有出处 引用台账 + 证据校验
可用 评审期在线 生产模式 + 反向隧道

三、系统架构

3.1 总体架构

┌─────────────────────────────────────────────────┐
│  浏览器                                          │
│   /chat  对话 + 家系图     /  风险量化 + 行动方案  │
└───────────────────┬─────────────────────────────┘
                    │ HTTP
┌───────────────────▼─────────────────────────────┐
│  Next.js 16 (App Router, TypeScript)            │
│   /api/extract  口述 → 家系节点                  │
│   /api/explain  依据检索（BM25）                 │
└───────────────────┬─────────────────────────────┘
                    │ localhost
┌───────────────────▼─────────────────────────────┐
│  llama.cpp server (127.0.0.1:8080)              │
│   Qwen3-1.7B Q4_K_M + GBNF 约束解码              │
└─────────────────────────────────────────────────┘

关键约束：整条链路上，家族病史一次都没有离开这台电脑。

3.2 四层分离

层 做什么 用什么 为什么不用大模型
① 理解层 口述 → 结构化节点 LLM ——
② 推断层 家系 → 家族史等级 词表 + 规则 这是亲缘映射问题，不是语言问题
③ 量化层 加可变因素 → 倍数拆解 FINDRISC 评分表 系数必须可查、可复现
④ 建议层 分数 → 动作 + 出处 RAG + 排序 阈值必须来自文献

为什么这样分：大模型只做它唯一不可替代的事——把口语变成结构。一旦涉及判断，就交给可复核的规则。这样无论换哪个模型，结论都不会变，只会影响抽取准确率。

3.3 技术选型

选择 备选 理由
Next.js 16 Vite + Express 前端与 API 同进程，部署简单；App Router 支持路由级代码分割
本地 llama.cpp 云端 API 隐私（数据不出机）、稳定性（不依赖额度与网络）、能用 GBNF
Qwen3-1.7B Q4_K_M 8B / 14B 1.2 GB，单次抽取 1–2 秒；家系抽取任务边界窄，不需要大模型
GBNF 约束解码 prompt 要求格式 从解码层保证合法 JSON，不是靠祈祷
BM25 检索 向量检索 语料仅 13 条，向量模型要多加载几百 MB，属过度设计
固定槽位布局 力导向图 家系结构本身确定；固定槽位下新节点出现时老节点不移动

四、AI 技术方案

本章对应评分表 35% 的 AI 技术深度，按「选型 → 集成 → 优化 → 评测」展开。

4.1 选型：为什么是本地小模型

隐私：家族病史包含「谁得了什么病、几岁死的」，属于最敏感的个人信息之一。走云 API 意味着这些文本会离开用户设备。本地推理把这条风险从根上消除，这不是技术偏好，是产品前提。

可用性：评审期需要服务在线。本地推理不依赖 API 额度、不依赖外网、不会被限流。

能力：GBNF 约束解码是 llama.cpp 独有的能力，云端只能靠 prompt 祈祷格式正确。

代价：模型小、能力弱。这个代价在 4.4 与 4.5 节用架构补回来。

4.2 模型

Qwen3-1.7B，Q4_K_M 量化，GGUF 格式，1.2 GB。

选它的理由：

  • 中文能力强于同参数量英文模型；
  • 1.7B 在 Q4 量化后仅 1.2 GB，加载快、显存占用低；
  • 单次抽取实测 1.0–2.1 秒（RTX 5080，CUDA），可接受交互延迟。

不支持思考模式（enable_thinking=false）：抽取任务不需要推理链，思考模式反而会让输出偏离格式。

4.3 GBNF 约束解码

做法：把输出的 JSON 结构编译成文法，模型只能在文法允许的 token 上采样。

root    ::= "{" ws "\"persons\"" ws ":" ws persons ws "}"
persons ::= "[" ws (person (ws "," ws person)*)? ws "]"
person  ::= "{" ... "\"relation\"" ws ":" ws rel ... "}"
rel     ::= "\"father\"" | "\"mother\"" | ... | "\"unknown\""
dis     ::= "\"心梗\"" | "\"冠心病\"" | ... | "\"其他\""

为什么枚举用中文而不是英文编码：

最初枚举用的是 liver-cancer、type2-diabetes 这类英文标识。实测发现：模型认得「肝癌」，但不知道它对应哪个英文串，新增病种的识别率接近零。

改成让模型输出中文病名、后端映射回内部编码之后，问题消失。不要求模型记住人为定义的标识符，是这次改造最大的收益。

枚举由词表派生：GBNF 的疾病枚举、界面上的中文标签，都由 DISEASES 一张表生成。此前病名写在三个地方，加一个病种漏改一处就会出 bug。

4.4 分句抽取架构

问题：1.7B 在「逗号分隔的多实体长句」上系统性失败。

输入 输出
我奶奶高血压，姥姥糖尿病 只抽出奶奶
我舅舅 45 岁糖尿病，外婆肺癌 只抽出舅舅

但「外婆和姨妈都有乳腺癌」这种用「和」并列的句子，反而能抽全。

方案：按句切开、逐句抽取、合并去重。

// 逗号只在非并列时切分：「外婆和姨妈都有」是一个整体
text.split(/[。；;]|(?<![和及与、])，/)

分句带出的三个新问题及修复（这是本次开发最值得记录的一段）：

新问题 现象 修复
主语被切丢 「我爷爷没熬过去，肺癌」→ 后半句没主语 无病名片段作为主语前缀累积，拼到下一片段
短片段凭空造病 「我妈那边」单独抽取 → 编出乳腺癌 无疾病词的片段直接跳过，不送模型
否定句被硬抽 「我妈身体还行」→ 抽出高血压 prompt 加规则 + 示例，整句健康则输出空

修完，口语集 F1 从 0.611 提升到 0.850。

4.5 三层校验

约束解码保证 JSON 合法，保证不了内容正确。所以在模型外面加了三层：

第一层：词表校正

模型会把「老爹」抽成伯叔、「二姨」抽成舅舅。但文本里明确写了称谓——这时以词表为准。

// 句中只出现唯一称谓时，用词表覆盖模型判断
// 「我爸和我叔都心梗」这种一句两人的，交给模型自己判断
if (mentioned.size !== 1) return person;

这里有个细节：「我妈那边，二姨有乳腺癌」中的「我妈」只是划定范围，不是主语。所以要排除「称谓 + 那边 / 这边 / 家」这类方位指代，否则校正会被带偏。

第二层：证据校验

每个抽出的病，必须在原句里找到对应说法，找不到就删除。实测出现过「我爸前年做了搭桥，那时候五十五」被抽出多余的脑卒中——原文根本没提。

口语集 Precision: 0.895 → 1.000
口语集 Recall:    0.810 → 0.762

注：上表是加入证据校验当时的即时影响。此后疾病词表从 9 种扩到 26 种、 补齐「放的支架」等谓语变体，分句时让无称谓续句继承主语，few-shot 补 「A 和 B 都 X」「主语那人，血压高」句式。微调模型在旧版 21 条口语集上达到过 Recall 1.000、F1 1.000；该模型当前无法在本机复现，数字统一标注「待复现」， 可复现的基线数字见 docs/accuracy.md。

这个交换是刻意的：在医疗场景里，漏掉一个病只是信息不全，编造一个病会让下游给出错误建议。宁可漏，不可编。

第三层：结果去重

模型偶尔把同一个人输出两次（GBNF 允许数组重复）。统一按关系合并 conditions 去重。

4.6 Few-shot 设计

11 个示例，覆盖三类系统性错误：

  1. 中文亲属称谓（父系 / 母系、一级 / 二级）
  2. 疾病口语说法（放支架、脑溢血、搭桥）
  3. 否定与并列表达（身体还行、和 / 顿号并列）

两条纪律：

  • 表述刻意与评测集不同。如果示例和测试句子一样，等于把答案塞进上下文，指标会虚高。
  • 示例必须像人说的话。踩过一次坑：「我爸 52 岁放的支架」不通——句中「的」是「的时候放的」省略了「的时候」，前面只能接模糊时间（「五十多岁放的支架」），接精确数字就不成立。改为「52 岁那年放了心脏支架」。

4.7 训练与推理的一致性

微调版本不使用 few-shot，让模型把称谓映射内化，推理时上下文更短。

为此，system prompt 抽到 src/lib/extract/prompt.ts 单独维护，训练数据生成器与线上推理都从这里 import——否则会出现「训练时见过的指令」和「推理时收到的指令」不一致，效果直接打折。

4.8 评测方法与结果

完整版（含留出集制度、失败分析、微调 A/B 对照、复现命令）见 docs/准确性说明.md。

自建两套评测集，同一套指标：

数字统一以 docs/accuracy.md 为准，每次评测自动落盘到 docs/eval-results/（含 commit 与模型）。 下方为 2026-11-09 用**基座模型（few-shot，未微调）**跑出的可复现结果； 微调模型的数字需要先导出合并后的 GGUF 才能复现，在那之前标注「待复现」，不对外承诺。

评测集 条数 Precision Recall F1 完全匹配
规整句 16 0.913 1.000 0.955 14/16
口语 v2 80 0.882 0.852 0.867 66/80

指标定义：把每个人 × 每种病展开成 (relation, code) 对，与人工标注比对，算 Precision / Recall / F1。年龄准确率单独统计（容差 ±2 岁）。完全匹配指整条输入的全部对与年龄都对。

为什么一定要有口语集：最初只有规整集，F1 0.927。后来意识到这些句子是开发者自己编的、偏书面、结构规整，于是另建一套刻意口语化的句子，同一套模型掉到 0.611。

这个 0.611 才是真实水平。承认它，然后才有后面的修复。

4.9 失败模式分析

当前仍存在的失败（诚实记录）：

类型 例子 原因
形容词性病名 「我奶奶老年痴呆」（无谓语）→ 漏抽 模型把它当成描述而非疾病；加「有」即正常
词表覆盖 「放了心脏支架」曾漏抽 子串匹配，「放了支架」命中不了「放了心脏支架」
多实体归属 「我爸 52 岁放支架，爷爷糖尿病」偶尔把爷爷的病挂到父亲身上 1.7B 的注意力分配能力限制
单条波动 同一输入两次结果可能不同 小样本下 temperature 0.1 仍有波动

4.10 微调尝试与阻塞

按计划生成了 1080 条训练数据（结构驱动：先构造语义结构再渲染成中文，标注 100% 准确，不依赖模型生成），并准备了完整的 LoRA 训练链路。

但训练被硬件架构阻塞：开发机为 RTX 5080（Blackwell，sm_120），预装的 PyTorch 为 cu126 构建，只编译到 sm_90，执行算子报 no kernel image is available。官方 cu128 wheel 在本地网络不可达，阿里云 PyTorch 镜像的下载速度约 90–600 KB/s，2.5 GB 需要一小时以上。

判断：此时 few-shot 方案已达 F1 0.952（规整）/ 0.857（口语）（2026-11-09 用 16/80 条集复测为 0.955 / 0.867，见 docs/accuracy.md），而微调能带来的确定性收益主要是「去掉 few-shot 提速」——但 cache_prompt 已让 few-shot 几乎不增加延迟。所以没有把时间押在训练上，转而补齐产品闭环与 RAG。

训练数据、词表、生成器、评测集全部保留在仓库中，环境具备后可随时接上。

五、核心功能实现

5.1 对话与抽取

用户在左侧输入口语，前端调 /api/extract，拿到结构化节点后合并进家系树，右侧图实时更新。

几个实现细节：

  • 合并而非覆盖：同一亲属可能被多段话提到（先说父亲心梗、后说父亲糖尿病），按关系合并 conditions 并去重，而不是覆盖。
  • 依据随行：onExtracted 回调同时返回本次的用户原话，页面把它存进 sources[relation]，供后续「依据回溯」使用。
  • 失败可见：推理服务未启动时，聊天区明确提示「请确认 llama-server 已在 8080 启动」，而不是静默失败。

5.2 家系图布局与渲染

布局用固定槽位，不用力导向：

力导向 固定槽位（本项目）
每次渲染位置 可能不同 恒定
新节点出现时 全图重排 老节点不动，只长出一个
语义 靠距离暗示 父系左、母系右、辈分自上而下

家系结构本来就是确定的，力导向是舍近求远。而且「新节点长出来、老节点不动」这个视觉，在演示里比「整张图重新排一次」强得多。

连线用正交折线（临床家系图标准画法），斜线会穿过节点。

三种情况的兜底：

  1. 祖辈 → 旁系列成「任一同系祖辈 → 该旁系」，避免用户只提到一位祖辈时旁系成为悬空孤点；
  2. 祖辈全缺时，旁系改用虚线同胞线连到父母；
  3. 同胞线走节点上方，避免横穿同排中间的其他节点。

符号语义：方形男性、圆形女性、实心表示有该病记录、空心表示未记录。这是临床家系图的通用约定，医生一眼能看懂。

5.3 风险量化

FINDRISC 八条目评分 + 风险分层 + 可回收风险反事实。

反事实的定义很直接：把可改变条目（BMI、腰围、体力活动、蔬果）全部设为 0 分，其余不动，重算总分。差出来的分数就是「可回收」的。

界面上是一条对数刻度的风险尺，两个标记点分别是「现在」和「全部达标后」，中间的橙色虚线就是可回收区间。

为什么用对数刻度：风险值范围 1%–50%，线性刻度会把低风险区压成一条线，看不出「从 33% 降到 4%」的落差。

反事实滑块：拖动 BMI / 腰围，右侧数字实时重算。技术上纯前端（模型已加载），毫秒级响应。这是产品里最直击的一屏——用户不是被告知风险，是自己试出来的。

5.4 行动方案

不列 8 条建议让人全做，按 分值 ÷ 难度 排序，只留 2 件本周能做的。

每条必须带最小动作：

方向（无效） 最小动作（有效）
多运动 先从每天 10 分钟开始，一周后加到 15 分钟
控制体重 晚饭主食减半，先坚持两周
健康饮食 午饭加一份青菜，别指望晚饭补

分值全部来自量规本身（做到 0 分能拿回多少），不引入未核实的外部效应量。

其余项折叠为「还有 2 项，等这两件稳住了再说」——不假装要求用户全改。

5.5 依据检索

用户可以对任何一个数字问「凭什么」。

实现为 BM25 检索：13 条已核实知识条目，中文按字符 2-gram 切分，阈值 1.8。

为什么不用向量检索：语料只有 13 条，向量模型要额外加载几百 MB、多一次推理往返。检索策略应当匹配语料规模，为小语料上向量模型是过度设计。

关键设计：检索不到时返回空，界面上明说「知识库里没有与这个问题匹配的条目，与其给一个听起来合理的答案，不如直接说没有」。实测「今天天气怎么样」正确返回未找到。

语料只收录 docs/references.md 中核实过的内容，每条带出处。

七、创新点

7.1 技术创新

1. 可回收风险（reclaimable risk）

把风险拆成「改不了的」（年龄、家族史、既往史）与「能拿回来的」（生活方式），并把后者变成一个可计算、可比较、能复算的数字。

这不是文案创新——它来自量规条目本身的分组性质，且反事实计算可被任何人用同一张量表复现。

2. GBNF 约束 + 三层校验的混合架构

约束解码保证格式，三层校验保证内容：

层 手段 解决
词表校正 符号规则 「老爹」被抽成伯叔
证据校验 原文比对 凭空多出一个病
合并去重 结构归一 同一人输出两次

这条链路的思路是：用确定性规则兜住不确定的模型，而不是指望模型自己变准。

3. 分句抽取解决小模型的多实体缺陷

1.7B 在长句里会漏掉第二个亲属。解法不是换更大的模型，而是改变输入形态——让模型每次只面对一个人。

配套解决了分句带来的三个副作用（主语丢失、空片段幻觉、否定误判）。

4. 中文标签枚举

要求模型输出 liver-cancer 这类人为标识符，识别率接近零；改成输出「肝癌」再后端映射，问题消失。

不要求模型记住人类定义的编码，是这次改造最大的收益，也可迁移到任何「模型输出 → 系统编码」的场景。

7.2 应用创新

1. 家系图从「报告」变成「可点开的底稿」

临床家系图画完就夹进病历，患者见不到第二次。这里每个节点都能点开：看它是从你哪句话抽出来的，也能直接删掉。

抽取结果可见、可改、可追溯——这是与黑盒 AI 最实质的区别。

2. 使用者与受益者分离

用户是成年子女，受益人是父母，而父母不配合。所以产品输出的是「能替你说服家人的东西」：可打印的图、可转发的提醒、能递给医生的清单。

3. 反馈降门槛，而不是催促

用户没做到时，正确的反应不是推送「该打卡了」，而是系统自己把门槛降下来：「15 分钟太长？先改成 8 分钟」。这个区别一眼可辨：前者在执行脚本，后者在重新规划。
